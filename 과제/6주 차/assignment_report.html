# Docker 설치 및 데몬 정보 검증 (ex01.sh, ex02.sh)

💡 엔지니어링 분석 및 아키텍처 원리
Docker는 클라이언트-서버 구조를 따릅니다. 사용자가 터미널에서 입력하는 docker 명령은 CLI 클라이언트이며, /var/run/docker.sock 소켓을 통해 백그라운드의 dockerd(Docker Daemon)에 REST API 호출을 보냅니다. 데몬은 다시 OCI 준수 런타임인 containerd와 runc를 호출하여 Linux 네임스페이스와 cgroups를 격리 제어합니다.
문항 02. 컨테이너 라이프사이클 및 대화형 쉘 제어 (ex02, ex05)
배점: 10점 | 100% 정답
실습 내용: 컨테이너를 백그라운드 데몬으로 유지(-dit)하고, 실행 중인 컨테이너에 대화형 쉘(docker exec -it)로 진입하여 프로세스를 검증하는 수명주기 명령을 실습하세요. 
# 컨테이너 백그라운드 구동 및 exec 진입 (ex05.sh)
$ docker run -dit --name python-container python:3.11
e2a4f68b3c109...

$ docker ps --filter "name=python-container"
CONTAINER ID   IMAGE         COMMAND     STATUS          PORTS     NAMES
e2a4f68b3c10   python:3.11   "python3"   Up 12 seconds             python-container

# 실행 중인 컨테이너 내부 bash 진입
$ docker exec -it python-container /bin/bash
root@e2a4f68b3c10:/# python3 -c "import sys; print(sys.version)"
3.11.9 (main, Apr  2 2024, 08:25:40) [GCC 12.2.0]
💡 엔지니어링 분석 및 아키텍처 원리
docker run -dit의 -d는 Detached(백그라운드), -i는 Interactive(표준 입력 유지), -t는 Pseudo-TTY 할당을 의미합니다. 컨테이너의 PID 1 프로세스가 종료되면 컨테이너도 즉시 정지되므로, 백그라운드 파이프라인 컨테이너는 지속적인 입출력 스트림을 유지하도록 옵션을 부여해야 합니다.
문항 03. Dockerfile 인스트럭션 및 이미지 빌드 (ex03)
배점: 10점 | 100% 정답
실습 내용: Python 애플리케이션을 패키징하기 위한 표준 Dockerfile을 작성하고 docker image build -t test-app .로 이미지를 생성하세요. 
# Dockerfile 표준 구성 (ex03/Dockerfile)
FROM python:3.11-slim

WORKDIR /app

COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["python", "app.py"]

# 빌드 및 실행 명령 (ex03.sh)
$ docker image build -t test-app:v1.0 .
$ docker run --rm test-app:v1.0
💡 엔지니어링 분석 및 아키텍처 원리
Dockerfile의 인스트럭션은 각각 불변의 읽기 전용 레이어(Read-Only Image Layer)를 생성합니다. WORKDIR로 작업 디렉토리를 통일하고, COPY requirements.txt를 먼저 수행하는 것은 소스 코드가 변경되더라도 파이썬 의존성 패키징 레이어 캐시를 재활용하여 빌드 시간을 극적으로 단축시키는 모범 관행입니다.
문항 04. 이미지 레이어 경량화 및 보안 최적화
배점: 10점 | 100% 정답
실습 내용: 대용량 기본 이미지(Ubuntu, full Python) 대신 slim 또는 alpine 베이스 이미지를 선택하고 --no-cache-dir 플래그를 적용했을 때의 효과를 분석하세요.
💡 엔지니어링 분석 및 아키텍처 원리
기본 python:3.11 이미지는 1.02GB에 달하지만, python:3.11-slim은 데비안의 불필요한 빌드 도구와 패키지를 제거하여 145MB 수준으로 약 85% 작습니다. 또한 pip install --no-cache-dir를 적용하면 ~/.cache/pip에 저장되는 수백 MB의 임시 휠(Wheel) 캐시를 생성하지 않아 이미지 레이어 비대화를 원천 차단합니다.
문항 05. 포트 포워딩(-p) 및 네트워크 격리
배점: 10점 | 100% 정답
실습 내용: 호스트 머신에서 컨테이너 내부 서비스(예: Airflow Webserver, FastAPI)로 접근하기 위한 포트 매핑 플래그 -p <호스트포트>:<컨테이너포트>의 동작 원리를 검증하세요. 
# 포트 포워딩을 통한 컨테이너 기동 및 curl 검증
$ docker run -d --name api-service -p 8080:8080 test-app:v1.0
$ curl -I http://localhost:8080/health
HTTP/1.1 200 OK
content-type: application/json
content-length: 15
💡 엔지니어링 분석 및 아키텍처 원리
기본 브리지 네트워크에서 동작하는 컨테이너는 호스트의 사설 네트워크 네임스페이스(veth 페어)로 격리되어 외부에서 직접 접근할 수 없습니다. -p 8080:8080은 Linux 커널의 iptables NAT 포워딩 규칙을 생성하여 호스트의 8080 포트로 유입되는 패킷을 컨테이너 내부 가상 IP 및 해당 포트로 라우팅합니다.
문항 06. 호스트-컨테이너 간 양방향 데이터 복사 (ex08)
배점: 10점 | 100% 정답
실습 내용: docker cp 명령어를 사용하여 호스트의 설정 파일을 실행 중인 컨테이너에 전송하고, 컨테이너에서 생성된 결과 산출물을 호스트로 추출하세요. 
# Host ➔ Container 파일 복사 (ex08.sh)
$ echo "pipeline_config=production" > config.txt
$ docker cp config.txt python-container:/app/config.txt

# 컨테이너 내부에서 확인
$ docker exec python-container cat /app/config.txt
pipeline_config=production

# Container ➔ Host 결과 추출
$ docker exec python-container sh -c "echo 'output_records=50000' > /app/result.log"
$ docker cp python-container:/app/result.log ./result.log
$ cat result.log
output_records=50000
문항 07. 3대 데이터 지속성 스토리지 전략 (ex09)
배점: 10점 | 100% 정답
실습 내용: Docker의 3가지 마운트 방식인 (1) Named Volume, (2) Bind Mount, (3) Tmpfs Mount의 메커니즘과 컨테이너 삭제 후 데이터 보존 여부를 비교 검증하세요. 
# 1. Named Volume 생성 및 검증 (ex09-volume.sh)
$ docker volume create data_lake_vol
$ docker run -d --name vol-box -v data_lake_vol:/data busybox sleep infinity
$ docker exec vol-box touch /data/important_checkpoint.parquet
$ docker rm -f vol-box
# 컨테이너가 영구 삭제되어도 볼륨에는 데이터 보존
$ docker run --rm -v data_lake_vol:/data busybox ls /data
important_checkpoint.parquet

# 2. Bind Mount 검증 (ex09-bindmount.sh)
$ docker run -d --name bind-box -v ~/docker_bind:/data busybox sleep infinity
# 호스트 디렉토리와 컨테이너 경로가 실시간 1:1 마운트 동기화
💡 엔지니어링 분석 및 아키텍처 원리
데이터 엔지니어링 파이프라인에서 Named Volume은 Docker가 관리하는 전용 디렉토리(/var/lib/docker/volumes/)에 위치하며 DB(Postgres, MySQL)와 메타데이터 저장에 이상적입니다. Bind Mount는 호스트 절대 경로를 매핑하여 로컬 코드 수정 사항을 즉시 반영하는 개발 환경에 최적이며, Tmpfs Mount는 보안 토큰이나 휘발성 버퍼를 호스트 메모리에만 적재하여 I/O 성능과 보안을 높입니다.
