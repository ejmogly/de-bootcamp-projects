# 8주차 제출 코드 리뷰 — 실무 관점 개선점

김준님이 요청하신 세 가지 관점(예외 처리·재시도 / 대용량·스큐·파티셔닝 / 클린 코드)으로,
제출하신 코드에서 개선 효과가 큰 지점을 정리했습니다.
행 번호는 제출하신 파일 기준이며, 같은 부분을 예시 답안(`01_예시답안_Q5_Q7_Q8`)에서 어떻게 처리했는지 함께 적었습니다.

## 1. 예외 처리 · 재시도

### Q1 `bronze_realestate_collect.py` — API 페이지 처리와 실패 신호
- **47행** `numOfRows=1000&pageNo=1` 로 한 번만 호출합니다. 한 달 거래가 1,000건을 넘는 시군구는 데이터가 잘립니다.
  응답의 `totalCount`를 보고 `pageNo`를 늘려 가며 모두 받는 루프가 필요합니다.
- **55~57행, 84~86행** 예외를 잡아 `{"status": "FAIL"}`을 반환하므로 task 자체는 성공 처리됩니다.
  네트워크 오류처럼 다시 시도하면 해결될 문제는 예외를 그대로 올리고, Airflow `retries` + `retry_exponential_backoff`에 맡기는 편이 재시도·알림 측면에서 낫습니다.
  "응답 0건"처럼 정상적인 분기만 반환값으로 처리하세요.

### Q7 `spark_job.py` — Redshift 대기 루프
- **108·133·152행** `while True:` + **113·138·156행** `time.sleep(1)`로 상태를 조회합니다. 제한 시간이 없어 Redshift 쪽 문제가 생기면 Pod가 끝나지 않습니다.
- **예시 답안:** `Q7/redshift_loader.py`의 `_wait()`가 1→2→4→8→10초 백오프와 600초 제한을 두고, `FAILED`·`ABORTED`면 에러 메시지와 함께 예외를 던집니다.

### Q7 `spark_job.py` — 적재 원자성
- **100행** `TRUNCATE TABLE` 후 별도 문장으로 `COPY`합니다. Redshift의 `TRUNCATE`는 즉시 커밋되므로, COPY가 실패하면 테이블이 빈 채로 남습니다.
- **예시 답안:** staging 테이블에 COPY한 뒤 `DELETE` + `INSERT … SELECT`로 교체하는 SQL 5개를 `batch_execute_statement` 하나로 실행합니다. 하나라도 실패하면 전체가 롤백되어 기존 데이터가 유지됩니다.

### Q2 · Q5 — 삭제 후 업로드
- Q2 **172행**, Q5 **102행**에서 S3 기존 객체를 먼저 지우고 새로 업로드합니다. 중간에 실패하면 데이터가 비어 버립니다.
- **실무 패턴:** 임시 prefix에 쓰고 완료 후 교체하거나, 실행 ID·날짜별 경로에 쓰고 최신 위치만 바꾸는 방식을 씁니다. Spark가 `s3a://`로 직접 `mode("overwrite")`를 쓰면 커밋 프로토콜이 이 과정을 처리합니다.

## 2. 대용량 · 스큐 · 파티셔닝

### Q2 `silver_spark.py` — 드라이버 파싱
- **56행** `ET.fromstring()`으로 XML을 드라이버에서 파싱하고, **110행** `createDataFrame(records)`로 파이썬 리스트를 DataFrame으로 만듭니다. 데이터가 커지면 드라이버 메모리가 병목이 됩니다.
- **권장:** `spark-xml`(또는 `binaryFile` + `mapPartitions`)로 executor에서 파싱하도록 바꿉니다.

### Q2 `silver_spark.py` — 시군구별 반복 계산
- **147~161행** 시군구마다 `filter` → `approxQuantile` → `union`을 반복합니다. 시군구 수만큼 Spark job이 돌아(제출하신 Spark UI 캡처에서 approxQuantile job이 60여 개) 실행 계획도 길어집니다.
- **권장:** `groupBy(시군구).agg(F.percentile_approx(평당가, [0.25, 0.75]))`로 경계값을 한 번에 구하고 join 후 필터합니다. job이 1~2개로 줄고, 특정 시군구에 거래가 몰리는 스큐에도 더 안정적입니다.

### Q5 `process_stocks.py` — 파일 수와 S3A 우회
- **95행** `coalesce(1)`은 소량 데이터에서는 괜찮지만, 데이터가 커지면 쓰기가 한 task에 몰립니다. Redshift COPY는 여러 파일을 병렬로 읽으므로 적당한 파일 수를 유지하는 편이 유리합니다.
- **31~41행** S3A 드라이버가 없으면 boto3로 내려받아 로컬에서 읽습니다. 이렇게 하면 S3 읽기가 분산되지 않습니다.
- **예시 답안:** `Q5/process_stocks.py`는 `--packages`로 S3A를 추가하고 `s3a://`로 직접 읽고 씁니다.

### Q7 — 컨테이너 안 local 모드
- `Dockerfile` **19행** `ENTRYPOINT ["python3", "/app/spark_job.py"]`는 Pod 하나 안에서 Spark를 local 모드로 실행합니다. 분산이 되지 않아 K8s에서 Spark를 쓰는 이점이 없습니다.
- **예시 답안:** `spark-submit --master k8s://… --deploy-mode client`로 드라이버가 executor 파드를 만듭니다. k3s 클러스터에서 executor 2개가 생성·등록되고 Job이 `1/1`로 끝난 뒤 executor가 정리되는 것까지 실측으로 확인했습니다.

## 3. Clean Code · 재사용성

### 설정값 하드코딩
- Q3 `gold_spark_sql.py` **105행** `current_year = 2026` — 해가 바뀌면 건축연식 분류(신축·준신축·구축)가 틀어집니다. `date.today().year`나 실행 기준일(`ds`)에서 계산하세요.
- Q3 **168행**과 `gold_realestate_aggregate.py` **31행** `postgresql://airflow:airflow@postgres:5432/airflow` — 접속 정보가 코드에 있습니다. Airflow Connection(`PostgresHook`)이나 환경 변수로 분리하세요.
- Q7 `spark_job.py` **18행** IAM Role ARN 기본값에 계정 번호가 들어 있습니다. 예시 답안은 버킷·계정 정보를 코드에 두지 않고 인자·환경 변수로 받습니다.

### 숨은 대체 경로
- Q3 **184~193행** `write.format("jdbc")`가 실패하면 `toPandas().to_sql()`로 대체합니다. 운영에서는 "조용한 다른 경로"가 원인 파악을 어렵게 만듭니다. 필요한 JDBC 드라이버를 이미지에 명시하고, 실패는 실패로 드러내세요.

### 로직 중복
- Q5와 Q7이 같은 정제·집계 로직을 각자 갖고 있습니다.
- **예시 답안:** Q5 모듈의 `clean()`, `aggregate()`를 Q7이 import해서 재사용합니다(Dockerfile이 두 모듈을 함께 담음). 로직을 고칠 때 한 곳만 바꾸면 됩니다.

### 이미지 태그
- Q7 `spark-job.yaml` **14~15행** `image: q8-spark-stock:latest` + `IfNotPresent` 조합은 이미지를 새로 빌드해도 노드에 캐시된 예전 이미지를 쓸 수 있습니다. 예시 답안처럼 `1.0.0` 같은 버전 태그를 쓰세요.

### Q8 — 수치 직접 입력
- `load_results.sh`에 종목별 수치를 직접 적었습니다. 예시 답안은 과제 05 결과 파일(`stock_stats.csv`)을 읽고, 종목 수와 파드 수가 다르면 중단합니다.
