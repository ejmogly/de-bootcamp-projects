문항 01. 분산 버전 관리 시스템 (DVCS) 아키텍처
배점: 10점 | 100% 정답
문제: Git과 같은 분산 버전 관리 시스템(DVCS)이 기존 중앙 집중식 버전 관리 시스템(CVCS, 예: SVN)과 비교했을 때 갖는 가장 핵심적인 구조적 차이점은 무엇인가요?
1 (1) 모든 개발자가 중앙 서버에 연결되어 있어야만 커밋을 수행할 수 있다.
2 (2) 모든 개발자의 로컬 환경에 전체 프로젝트 히스토리를 가진 완전한 복제 저장소가 존재한다. (선택한 정답)
3 (3) 파일의 변경사항을 네트워크를 통해서만 추적할 수 있다.
4 (4) 브랜치를 생성하거나 전환할 때 중앙 서버 관리자의 승인이 필수적이다.
💡 엔지니어링 분석 및 아키텍처 원리
DVCS의 핵심은 각 클라이언트가 프로젝트의 최신 스냅샷뿐만 아니라 전체 저장소(Repository)의 히스토리와 메타데이터를 통째로 로컬에 복제(Mirror)한다는 점입니다. 이를 통해 개발자는 네트워크 연결 없이도 오프라인에서 자유롭게 커밋, 브랜치 생성, 변경 이력 탐색을 즉각 수행할 수 있으며, 중앙 서버 장애 시에도 어떤 개발자의 로컬 복제본으로든 원본 저장소를 100% 복구할 수 있는 고가용성을 확보합니다.
문항 02. Git 3단계 작업 영역과 git add 메커니즘
배점: 10점 | 100% 정답
문제: Git에서 로컬 파일의 변경사항을 추적하고 영구 기록하기까지 거치는 3가지 상태(Working Directory, Staging Area, Git Repository) 중, git add 명령어를 실행했을 때 파일이 배치되는 영역은 어디인가요?
1 (1) Working Directory (작업 디렉토리)
2 (2) Remote Repository (원격 저장소)
3 (3) Staging Area (인덱스 / 준비 영역) (선택한 정답)
4 (4) Git Stash (임시 보관함)
💡 엔지니어링 분석 및 아키텍처 원리
git add 명령어는 Working Directory에서 수정한 파일 중 다음 커밋에 포함할 대상을 선별하여 Staging Area(Index)에 등록하는 단계입니다. Git이 변경점만을 단순 자동 기록하지 않고 Staging Area를 거치게 설계된 이유는, 엔지니어가 하나의 커밋에 관련된 논리적 변경사항만을 원자적(Atomic)으로 묶어서 기록할 수 있도록 격리 계층을 제공하기 위함입니다. 
# 파일 상태 확인 및 Staging Area 등록 실습
$ git status
# Changes not staged for commit:
#   modified:   dags/spark_batch_dag.py

$ git add dags/spark_batch_dag.py
$ git status
# Changes to be committed: (Staged 상태 확인)
#   modified:   dags/spark_batch_dag.py
문항 03. Git 커밋(Commit)의 본질과 스냅샷 구조
배점: 10점 | 100% 정답
문제: Git에서 git commit을 통해 생성되는 커밋에 대한 설명으로 가장 정확한 것은 무엇인가요?
1 (1) 단순히 이전 버전과의 텍스트 차이점(Diff/Delta)만을 저장한 텍스트 파일이다.
2 (2) 원격 서버에 즉시 전송되어 다른 사용자에게 자동으로 공유되는 단위이다.
3 (3) 특정 시점의 전체 프로젝트 파일 상태를 스냅샷 형태로 기록한 불변(Immutable) 객체이다. (선택한 정답)
4 (4) 실행 후에는 커밋 메시지나 내용을 절대 수정할 수 없다.
💡 엔지니어링 분석 및 아키텍처 원리
Git의 커밋 객체는 파일 변경 차분(Delta)을 누적하는 기존 VCS와 달리, 특정 시점의 전체 프로젝트 디렉토리 상태를 가리키는 루트 트리(Tree) 스냅샷과 부모 커밋 포인터, 작성자 정보, 커밋 메시지를 담은 불변의 DAG(Directed Acyclic Graph) 노드입니다. 고유한 SHA-1(40자리 16진수) 해시로 무결성이 검증되므로 데이터 변조가 물리적으로 불가능합니다.
문항 04. 원격 저장소 동기화: git pull vs git fetch
배점: 10점 | 100% 정답
문제: 원격 저장소(GitHub)의 최신 변경사항을 로컬로 가져오는 명령어 중, 원격 브랜치의 커밋을 다운로드함과 동시에 현재 로컬 브랜치에 자동으로 병합(Merge)까지 완료하는 명령어는 무엇인가요?
1 (1) git fetch
2 (2) git pull (선택한 정답)
3 (3) git clone
4 (4) git checkout
💡 엔지니어링 분석 및 아키텍처 원리
git pull은 내부적으로 git fetch(원격 변경사항을 다운로드하여 원격 추적 브랜치 origin/main을 갱신)와 git merge origin/main(현재 로컬 브랜치에 자동 병합)을 연속 수행하는 복합 명령어입니다. 안전한 협업 환경에서는 곧바로 pull하기보다, 먼저 fetch로 원격 변경점을 다운로드한 뒤 git log HEAD..origin/main으로 변경 이력을 검토하고 안전하게 병합하는 것이 권장됩니다.
문항 05. 머지 충돌(Merge Conflict) 원인 및 해결 절차
배점: 10점 | 100% 정답
문제: 여러 개발자가 Git으로 협업할 때, 두 개의 브랜치를 병합하는 과정에서 자동으로 병합되지 않고 ‘Merge Conflict(머지 충돌)’가 발생하는 원인으로 가장 적절한 것은 무엇인가요?
1 (1) 두 브랜치에서 서로 다른 파일을 추가하고 커밋했을 때
2 (2) 두 브랜치에서 동일한 파일의 서로 다른 라인을 수정했을 때
3 (3) 두 브랜치에서 동일한 파일의 동일한 코드 라인을 서로 다르게 수정했을 때 (선택한 정답)
4 (4) 원격 저장소의 용량이 초과되었을 때
💡 엔지니어링 분석 및 아키텍처 원리
Git의 3-way Merge 알고리즘은 공통 조상(Base) 대비 서로 다른 파일이나 동일 파일 내 다른 라인의 수정은 자동으로 병합합니다. 그러나 동일한 파일의 동일한 위치를 서로 다른 내용으로 수정한 경우 Git은 어느 쪽이 올바른 비즈니스 로직인지 임의로 판단할 수 없으므로 충돌 마커(<<<<<<< HEAD, =======, >>>>>>> branch)를 파일 내에 삽입하고 개발자에게 수동 결정을 위임합니다. 
# 충돌 해결 워크플로우
# 1. 파일 내 충돌 마커 확인 및 올바른 코드로 정리
<<<<<<< HEAD
REDSHIFT_PORT = 5439
=======
REDSHIFT_PORT = int(os.getenv("REDSHIFT_PORT", 5439))
>>>>>>> feature/env-config

# 2. 해결 후 스테이징 및 머지 커밋 완료
$ git add config.py
$ git commit -m "fix(config): resolve merge conflict on REDSHIFT_PORT setting"
문항 06. Git-Flow 브랜치 모델과 Hotfix 전략
배점: 10점 | 100% 정답
문제: 표준 Git-Flow 브랜치 전략에서, 이미 상용(Production) 서비스에 배포된 master(main) 브랜치에서 치명적인 긴급 버그가 발견되었을 때 이를 즉시 수정하기 위해 생성하는 전용 브랜치는 무엇인가요?
1 (1) Feature 브랜치
2 (2) Develop 브랜치
3 (3) Release 브랜치
4 (4) Hotfix 브랜치 (선택한 정답)
💡 엔지니어링 분석 및 아키텍처 원리
Git-Flow에서 일반적인 기능 개발은 develop에서 파생된 feature 브랜치에서 진행되지만, 상용 운영 환경의 장애는 대기 중인 다음 버전 개발 내용이 포함되지 않아야 합니다. 따라서 master(main)에서 직접 분기한 Hotfix 브랜치에서 결함을 최소한으로 수정하여 즉각 master에 머지(태그 생성)하고, 동일한 수정 사항을 반드시 develop 브랜치에도 역머지(Back-merge)하여 버그 재발을 방지합니다.
문항 07. 미커밋 변경사항 임시 보관: git stash
배점: 10점 | 100% 정답
문제: 현재 브랜치에서 작업을 진행하던 중 아직 커밋하기에는 미완성인 변경사항이 있는 상태에서, 다른 긴급 브랜치로 전환해야 합니다. 이때 작업 중이던 변경사항을 안전하게 임시 보관소에 저장하고 워킹 디렉토리를 깨끗하게 비우는 명령어는 무엇인가요?
1 (1) git clean -fd
2 (2) git stash (선택한 정답)
3 (3) git reset --hard
4 (4) git revert HEAD
💡 엔지니어링 분석 및 아키텍처 원리
git stash는 워킹 디렉토리와 Staging Area의 추적 대상 변경사항을 임시 저장 스택(Stack)에 안전하게 백업하고, HEAD 커밋 상태로 워킹 디렉토리를 롤백하여 브랜치 체크아웃 충돌을 방지합니다. 긴급 작업을 마친 후 git stash pop 명령어로 최신 보관 작업을 다시 적용하고 스택에서 제거할 수 있습니다.
문항 08. 커밋 히스토리 선형화: git rebase vs git merge
배점: 10점 | 100% 정답
문제: 브랜치를 병합할 때 독립적인 추가 '머지 커밋(Merge Commit)'을 생성하여 갈래를 남기지 않고, 현재 브랜치의 커밋들의 시작점(Base)을 대상 브랜치의 최신 커밋 뒤로 재배치하여 히스토리를 깔끔한 일직선(Linear History)으로 정돈하는 명령어는 무엇인가요?
1 (1) git cherry-pick
2 (2) git rebase (선택한 정답)
3 (3) git branch -m
4 (4) git merge --no-ff
💡 엔지니어링 분석 및 아키텍처 원리
git merge는 두 갈래의 히스토리를 보존하면서 새로운 병합 커밋(Diamond 형상)을 만듭니다. 반면 git rebase는 현재 브랜치의 커밋들을 임시 저장소에 두고, 베이스를 대상 브랜치의 HEAD로 이동시킨 뒤 커밋들을 하나씩 순차 재적용(Re-apply)합니다. 이를 통해 복잡한 분기선 없이 완전한 선형 히스토리를 유지할 수 있어 대규모 엔터프라이즈 레포지토리의 이력 추적성을 극대화합니다.
문항 09. 보안 및 거버넌스: .gitignore 파일 설정
배점: 10점 | 100% 정답
문제: 데이터 엔지니어링 프로젝트 저장소에서 API 자격증명이 담긴 .env 파일, 파이썬 가상환경(.venv/), OS 임시 파일(.DS_Store), 대용량 데이터 덤프(*.parquet) 등이 실수로 Git에 추적되거나 커밋되지 않도록 제외 규칙을 정의하는 설정 파일은 무엇인가요?
1 (1) .gitignore (선택한 정답)
2 (2) .gitattributes
3 (3) .gitconfig

💡 엔지니어링 분석 및 아키텍처 원리
Pull Request (PR)는 단순한 코드 병합 요청을 넘어, 현대 소프트웨어/데이터 엔지니어링 품질 거버넌스의 핵심 관문(Quality Gate)입니다. PR 템플릿을 통해 비즈니스 변경 목적, 테스트 결과, 데이터 파이프라인 영향도 분석을 문서화하며, GitHub Actions와 연계하여 린트 검사(Ruff/Black), 단위 테스트(Pytest), 보안 검사를 자동 통과해야만 머지가 승인되도록 통제합니다.
