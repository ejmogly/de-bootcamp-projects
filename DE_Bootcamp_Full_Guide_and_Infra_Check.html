📖 2. 처음부터 지금까지: 스텝바이스텝 리마인드 가이드

데이터 엔지니어링 부트캠프에서 다룬 방대한 내용들을 "데이터의 흐름" 순서대로 6단계로 쉽게 풀어서 정리했습니다.

Step 1. 데이터 창고(DW) 설계와 SQL 쿼리 최적화
1~2주 차 · ClassicModels DW

무엇을 했나요? 글로벌 모형 차량 유통사(ClassicModels)의 8개 테이블(고객, 주문, 상세품목, 결제, 지사, 직원 등)을 연결하며 기초 조회부터 다차원 집계, 다중 조인까지 30개의 분석 쿼리를 완성했습니다.

💡 리마인드 핵심: 왜 SELECT *를 쓰지 않고 WHERE에서 먼저 필터링할까요? 나중에 배운 컬럼형 파일(Parquet)과 클라우드 쿼리 엔진(Athena)은 "읽어들인 데이터 용량"만큼 과금되기 때문에, 필요한 컬럼과 행만 최소한으로 읽는 습관이 모든 데이터 파이프라인 최적화의 출발점입니다.
Step 2. 클라우드 데이터 레이크와 자동화 배관 공사
3~4주 차 · AWS S3/Glue/Athena & Airflow 3.0

무엇을 했나요? 내 컴퓨터에 데이터를 두는 대신 Amazon S3(데이터 레이크)에 파일을 올리고, AWS Glue로 스키마 카탈로그를 만든 뒤 Amazon Athena로 서버 없이 SQL 분석을 수행했습니다. 그리고 이 일련의 과정을 Apache Airflow 3.0(@dag, @task TaskFlow API, Dynamic Task Mapping)으로 자동화했습니다.

💡 리마인드 핵심: 파이프라인 자동화에서 가장 중요한 단어는 멱등성(Idempotency)입니다. 장애가 나서 어제 자 파이프라인을 세 번 다시 돌려도(Backfill), 데이터가 3배로 중복 적재되지 않고 언제나 똑같은 결과를 보장하도록 설계해야 합니다.
Step 3. 대용량 분산 처리 엔진으로 데이터 요리하기
5주 차 · Apache Spark (PySpark)

무엇을 했나요? 설비 IoT 센서 로그와 채용 공고 데이터를 PySpark로 분산 처리하고, 실행 계획(explain())을 분석해 처리 속도를 높이는 최적화를 진행했습니다.

💡 리마인드 핵심: Spark에서 가장 비싼 작업은 여러 서버가 네트워크로 데이터를 섞는 셔플(Shuffle)입니다. 큰 로그 테이블과 작은 마스터 테이블을 조인할 때 작은 테이블을 모든 워커 노드에 복제해 주는 Broadcast Join을 쓰면 셔플 없이 빠르게 처리할 수 있습니다.
Step 4. 컨테이너 인프라와 실전 End-to-End 데이터 파이프라인
6~8주 차 · Docker, Kubernetes & 부동산/주식 파이프라인

무엇을 했나요? Docker와 Kubernetes(K3s/k3d) 위에 Airflow와 Spark 클러스터를 띄우고, 외부 API(부동산 실거래가, 주식 데이터) 수집 ➔ S3 Raw 보존 ➔ Spark Parquet 정제 ➔ Redshift Serverless / PostgreSQL 마트 적재까지 이어지는 전 과정을 하나로 묶었습니다.

💡 리마인드 핵심: 데이터를 바로 DB에 넣지 않고 굳이 S3 Raw Zone(원본)과 Processed Zone(Parquet)을 거치는 이유는, 나중에 비즈니스 로직이 바뀌거나 버그가 발견되었을 때 언제든 원본 파일로부터 데이터를 다시 재생산(Replay)하기 위해서입니다.
Step 5. 초 단위로 흐르는 실시간 이벤트 스트리밍
9~10주 차 · Apache Kafka, KRaft, Connect, ksqlDB

무엇을 했나요? 전기차 충전소 상태 스트림과 실시간 가격 데이터를 다루기 위해 3대 브로커 기반의 Kafka 클러스터(KRaft 모드)를 구축하고, Schema Registry(Avro), Kafka Connect(S3/JDBC 연동), ksqlDB(5분 윈도우 실시간 이상 감지)까지 10개 실전 문제를 모두 해결했습니다.

💡 리마인드 핵심: Kafka는 같은 메시지 Key(예: 기기 ID, 주문 ID)를 가진 이벤트를 항상 같은 Partition에 순서대로 넣습니다. 덕분에 분산 환경에서도 특정 주문이나 센서의 상태 변화 순서가 뒤바뀌지 않게 보장할 수 있습니다.
Step 6. [현재 진행 중] 실시간 CDC 레이크하우스 스터디
사이드 프로젝트 1~3회차 완료 (4~8회차 예정)

무엇을 하고 있나요? 서비스 DB(PostgreSQL)에서 데이터가 추가(c), 수정(u), 심지어 물리 삭제(d)될 때, DB의 트랜잭션 로그(WAL)를 Debezium으로 실시간 캡처해 Kafka ➔ Flink ➔ Apache Iceberg (Bronze)로 적재하는 파이프라인입니다.

  • 1~2회차 완료: 9개 컨테이너 기동, 환불 20,000원 생성 ➔ 30,000원 수정 ➔ 삭제(환불 철회) 후 MinIO S3에 쌓인 실제 Parquet 파일 바이트와 Iceberg 메타데이터 트리 검증 완료.
  • 3회차 완료: 원천 INSERT부터 Bronze 조회까지 6.56초 지연 실측 완료. 나만의 개인 프로젝트인 "스마트 퀵커머스 실시간 주문·물류·정산 레이크하우스"(ecommerce.orders, payments, deliveries) 설계 및 원천 DB 테이블 생성 완료!
  • 다음 할 일 (4~8회차): Spark SQL로 Silver MERGE INTO 구현(4회차) ➔ dbt로 Gold 정산/SLA 마트 구축(5회차) ➔ 소급 정정(6회차) ➔ Iceberg 파일 컴팩션 튜닝(7회차) ➔ Airflow 연동(8회차).
