# 3회차 시연영상 따라하기 안내

이번 영상에서는 내 컴퓨터에서 **주문·결제 준비 → 환불 20,000원 생성 → 30,000원 정정 → 삭제**를 실행하고, 원천·Kafka·Iceberg Bronze에 무엇이 남는지 확인합니다. MinIO의 실제 파일을 살펴보고, 별도의 새 환불로 첫 조회까지 걸린 시간도 측정합니다.

**영상은 약 19분 55초입니다.** 설치와 실행에 필요한 시간은 따로 잡아주세요. 명령을 입력하거나 결과를 읽을 때는 영상을 멈춰도 됩니다.

긴 명령은 영상에서 받아 적기보다 가이드의 **한 블록 전체**를 복사하세요. SQL 파일도 같은 저장소에 들어 있습니다.

## 시작하기 전에

- Git, Python 3.9 이상, curl, Docker Engine과 Docker Compose v2를 준비하고 Docker를 켭니다. `curl --version`도 확인해주세요. curl은 bootstrap의 상태 확인에 사용합니다.
- Mac·Linux에서는 Bash 터미널, Windows에서는 Docker가 연결된 WSL의 Bash 터미널을 사용합니다. 검증 기준은 Linux ARM64 Docker 환경입니다.
- 명령은 **자기 컴퓨터의 cdc-lakehouse-study 폴더에서 같은 터미널**에 순서대로 입력합니다. 강사 서버 접속이나 SSH 터널은 필요하지 않습니다.
- 처음 설치·기존 환경 재시작·실행 중 환경 중 자신의 상태에 맞는 경로 하나를 고릅니다. 기존 `.env`를 덮어쓰지 않습니다.

영상의 저장소 clone·업데이트는 새 폴더에서 실제로 실행한 기록입니다. **처음 환경 설치는 방법을 안내하고, 파이프라인 실습은 이미 기동된 맥미니 Docker 랩의 실제 실행 기록으로 보여드립니다.** 화면 대기를 줄인 곳과 결과를 읽도록 멈춘 구간이 있으므로 영상 재생 시간을 처리 지연으로 읽지는 않습니다.

bootstrap은 초기 Silver·Gold까지 준비합니다. 이번에 새로 만드는 사건은 **Bronze까지만** 확인하며 마트 갱신은 진행하지 않습니다.

## 이렇게 따라오세요

1. 화면에 명령이 보이면 일시 정지하고, 가이드의 같은 블록을 실행합니다.
2. 실행이 끝난 뒤 표시한 필드와 값을 확인합니다. `wait`는 새 적재를 시작하는 명령이 아니라, 기대한 변경이 Bronze에 보이는지 조회하는 도구입니다.
3. **자신의 CASE_ID를 새로 만들고 출력값을 메모합니다.** 영상의 키를 복사하지 않습니다. 터미널을 새로 열면 변수도 다시 설정해야 합니다.
4. INSERT·UPDATE·DELETE는 각 단계에서 한 번씩 실행합니다. 지연 측정은 앞의 완료 키와 다른 **LATENCY_CASE_ID**로 주문·결제만 준비합니다. 환불은 측정 프로그램이 한 번만 입력합니다.
5. metadata 파일명·Parquet 경로·snapshot ID·offset·관측 시간은 각자 다릅니다. 자신의 출력으로 다음 화면을 찾고, 영상 속 번호와 같게 맞추지 않습니다. JSON reader의 `METADATA_FILE`도 자신의 다운로드 경로·파일명으로 바꿉니다.

공통 예제를 한 번씩 실행했을 때 같은 환불 키의 기대값입니다. 전체 테이블이나 토픽의 건수가 아닙니다.

| 변경 | 원천의 현재 환불 | Bronze 누적 이력 |
|---|---|---|
| 20,000원 생성 | 1건·20,000원 | c 1행 |
| 30,000원 정정 | 1건·30,000원 | c/u 2행 |
| 환불 삭제 | 0건 | c/u/d 3행 |

삭제까지 끝나면 Kafka에는 같은 키의 c/u/d와 tombstone, 누적 4개 레코드가 기대됩니다. d의 `after=null`과 tombstone의 value 전체 null은 다릅니다.

## 막혔을 때

- **Docker 연결 오류:** Docker가 켜졌는지, `docker version`에 Server 응답이 있는지 확인합니다.
- **원천 결과가 다름:** 자신의 CASE_ID와 `source-check.sql` 결과부터 확인합니다. 요약 표의 행 수와 실제 환불 수를 구분하세요.
- **Kafka에는 있는데 Bronze에 없음:** 같은 키·토픽·조회 조건을 확인한 뒤 Flink 입력·checkpoint·sink 오류를 봅니다. Kafka UI의 검색은 Enter로 적용하고 Refresh합니다.
- **JSON 파일을 못 찾음:** 다운로드 폴더와 파일명을 확인합니다. 원본 파일을 수정하거나 Catalog 포인터를 바꾸지 않습니다.
- **INSERT 응답 오류·측정 timeout:** 이미 commit됐을 수 있으므로 같은 변경을 바로 반복하지 않습니다. 마지막 명령·오류와 현재 원천 상태를 남깁니다.

결과를 맞추려고 볼륨·Kafka offset·버킷 파일을 지우지 않습니다. 질문할 때는 **내 CASE_ID, 마지막 명령, 오류, 어디까지 확인했는지**를 함께 적어주세요. 비밀번호·토큰은 올리지 않습니다.

끝나면 두 CASE_ID, 관측 결과, 질문 하나를 메모합니다. 개인 환경을 종료할 때는 가이드의 `./scripts/stop.sh`로 복구 지점을 남기며 중지합니다. 지연 측정값에는 폴링·REFRESH·쿼리·응답이 포함되므로 순수 Iceberg commit 지연이나 SLA로 해석하지 않습니다.
